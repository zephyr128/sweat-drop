## 8. Step 7 Recommendation

### Decision: **Step 7 migration NOT needed.**

**Rationale:**
1. **Zero drops came from cross-talk sessions.** Every session where the app was connected to a wrong machine lasted < 120 s (the minimum for `award_drops` to issue any drops). The server-side floor prevented any economy contamination even without the peripheral_id_mismatch guard (which was only added by Step 4 today).
2. **user_a's 31 session drops are clean.** Both sessions were on machine `eb9c8644`, lasted 19.5 min + 3.4 min at 5–6 km/h — consistent with real treadmill use. Nothing to reverse.
3. **user_b has 0 session drops.** The 8.5 km/h session was 59 s long; the threshold saved the economy here.
4. **No other Vortex users were affected.**

### No remediation SQL is needed. Close Step 7 as N/A.

If product still wants to issue a goodwill gesture (e.g., bonus drops for the poor UX), that is a product decision and should be done as a manual operation, not a fraud-remediation migration.

## 9. Ancillary Finding: checkin_too_far (user_a)

18 GPS geofence events across 3 days (2026-05-05, 2026-05-06, 2026-05-08). The gym is configured in **lenient** check-in mode, so all check-ins succeeded (10 drops each) despite the GPS distance warning. This is a separate issue from cross-talk:
- Either user_a was outside the gym's configured radius at the time of check-in (Vortex may have a tight GPS radius and user was near the entrance but not within it)
- Or GPS was inaccurate (indoor GPS, phone pocket)

**Recommendation:** Review the Vortex gym's GPS radius configuration in the admin panel. If the radius is < 100 m, widen it to 150–200 m to reduce GPS noise. This is unrelated to the cross-talk fix.
